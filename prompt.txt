## Purpose

The project is an **admin/build tool** for a future music game ("odd track" style). The admin curates audio clips from three sources, cuts them with FFmpeg, stores them in Cloudflare R2 + D1, and the game client will read from Cloudflare. The admin tool is not a runtime dependency.

## Database schema

```sql
-- genres
CREATE TABLE genres (
  id INTEGER PRIMARY KEY,
  name TEXT NOT NULL UNIQUE,
  display_name TEXT NOT NULL,
  image TEXT,
  is_customized INTEGER NOT NULL DEFAULT 0
);

-- artists (music artists OR quran reciters)
CREATE TABLE artists (
  id INTEGER PRIMARY KEY,
  name TEXT NOT NULL,
  genre_ids TEXT NOT NULL DEFAULT '[]',  -- JSON array of ints
  image TEXT,
  tracks_count INTEGER NOT NULL DEFAULT 0,
  is_customized INTEGER NOT NULL DEFAULT 0,
  created_at TEXT NOT NULL DEFAULT (datetime('now')),
  updated_at TEXT NOT NULL DEFAULT (datetime('now'))
);

-- tracks: ONE ROW PER SLOT, not per rendition
CREATE TABLE tracks (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  name TEXT NOT NULL,
  artist_id INTEGER,
  r2_key TEXT,                -- forward rendition (nullable)
  r2_reversed_key TEXT,       -- reversed rendition (nullable)   ← added via migration
  position TEXT,              -- start | middle | end | custom
  label TEXT
);
CREATE INDEX idx_tracks_artist_id ON tracks(artist_id);
CREATE INDEX idx_tracks_position  ON tracks(position);
CREATE UNIQUE INDEX idx_tracks_unique_clip ON tracks(artist_id, name, position);
```

**Key semantics:**
- One row = one "slot" = (artist_id, name, position). Both forward and reversed renditions of that slot live on the SAME row.
- Either `r2_key` or `r2_reversed_key` may be NULL. Both may be set.
- The unique index is on `(artist_id, name, position)` — you can't have two slots with the same combination, but you CAN have forward-only, reversed-only, or both.
- `id` is auto-generated. No matb3aa/mp3quran track ID is stored.
- Custom artists use IDs in the 90000+ namespace (matches the source `is_customized = 1` marker).
- A separate `DELETE /tracks/:id/reversed` endpoint clears only the reversed key (and R2 object). `DELETE /tracks/:id` removes the whole slot. There is no "delete forward only" — intentional.

## R2 key structure

```
clips/track-{trackId}-{position}-{N}s.mp3            (music, forward)
clips/track-{trackId}-{position}-{N}s-rev.mp3        (music, reversed)
clips/quran/track-{trackId}-{position}-{N}s[-rev].mp3
clips/upload/track-{trackId}-{position}-{N}s[-rev].mp3
```

For `custom` position, the key includes the start offset:
```
clips/upload/track-{trackId}-custom-{startSec}s-{durationSec}s[-rev].mp3
```

**`trackId` for uploads:** server-generated `9000000 + (Date.now() % 1000000) + fileIndex`. Not the DB row id. The value is only used for R2 key namespacing.

**Worker route for `/clips/:trackId`** accepts `[\w-]+` (not just digits) so upload/reverse flows work.

## FFmpeg pipeline

`publishClip` (server/lib/publish-clip.js) produces ONE rendition and uploads to R2. **It does NOT write to D1** — the caller does.

Stages: resolve source → (download OR copy from disk) → probe duration → compute effective startSec → FFmpeg extract → R2 upload → return `{ r2_key, size_bytes, position, duration_ms, reversed, start_sec, true_duration_sec, serveUrl, timings, elapsed }`.

FFmpeg args:
- **Forward:** `-ss {startSec} -i {in} -t {dur} -acodec libmp3lame -ab 24k -ac 1 -ar 22050 -compression_level 9 -y {out}`
- **Reversed:** `-ss {startSec} -i {in} -af "atrim=duration={dur},areverse" -acodec libmp3lame -ab 24k -ac 1 -ar 22050 -compression_level 9 -y {out}`

Critical: for reversed, `-t` is **replaced** by `atrim=duration=N` inside the filter graph so `areverse` sees exactly N seconds, not the tail of the file.

`reverseExistingClip` (also in publish-clip.js) takes an existing forward R2 key, downloads it via `/clips/serve?key=`, runs `-i {in} -af areverse ...` (no trim — the clip is already trimmed), uploads to `&reversed=1`, returns the new reversed key. It also does not write to D1.

## Cloudflare Worker endpoints (confirmed working)

Base URL: `https://music-game-wrangler.abdulrahman-muhammad2090.workers.dev`

**Tracks:**
- `GET /tracks` — list. Query: `?artist_id=&position=&search=&has_forward=0|1&has_reversed=0|1`. Returns `{ tracks, count }`. **This route must be registered in `trackRoutes` before `/tracks/:id`.**
- `GET /tracks/:id` — single slot (includes both r2 keys)

- `DELETE /tracks/:id/reversed` — clears only `r2_reversed_key` and its R2 object

**Clips:**
- `POST /clips/:trackId?position=&duration=&start=&source=&reversed=0|1` — accepts binary, stores to R2, returns `{ ok, r2_key, size_bytes, position, duration_ms, source, reversed }` with status 201
- `GET /clips/serve?key=<urlencoded r2 key>` — streams from R2
- `GET /clips/:trackId/:position` — head check
- `DELETE /clips/:trackId/:position` — delete

## Express server routes

All under `/api`. Two families:

**`/api/genres`, `/api/artists`, `/api/albums`, `/api/search`, `/api/quran`** — proxy to matb3aa and mp3quran.

**`/api/cloudflare/*`** — proxy to Worker, plus orchestration:
- `GET /tracks` — list (proxies Worker)
- `PUT /tracks/:id`, `DELETE /tracks/:id`, `DELETE /tracks/:id/reversed` — proxies
- `POST /tracks/publish-clip` — one-off single slot publish (forward and/or reversed)
- `POST /tracks/publish-clips` — batch publish. Each clip entry = ONE slot with `forward`/`reversed` flags. Concurrency 3. Calls `publishAndSaveSlot` helper.
- `POST /tracks/publish-upload` — multipart upload (multer diskStorage, project-local temp dir), 1–50 files, per-position Fwd/Rev config, concurrency 4 across files
- `POST /tracks/:id/reverse` — takes a slot's existing forward R2 key, calls `reverseExistingClip`, PUTs the new reversed key onto the same row. Body `{ replace: true }` if the slot already has a reversed rendition.

**`publishAndSaveSlot` helper** (in `server/routes/cloud-flare-routes/clips.js`):
Given `{ trackId, sourceSrc, name, artistId, position, duration, forward, reversed, label, source }`, it:
1. Calls `publishClip` for forward (if requested)
2. Calls `publishClip` for reversed (if requested)
3. POSTs ONE `/tracks` row with `r2_key` and `r2_reversed_key`
4. On 409, fetches existing row via `/tracks?artist_id=&search=` and PUTs to merge the new keys

## Frontend data flow

`useCloudflareTracks()` fetches:
- `GET /api/cloudflare/tracks` (all slots)
- `GET /api/cloudflare/artists` (for artist names)

Then **expands each slot row into up to two "clip" objects**:
```js
{
  id: '216:fwd',          // composite, unique per rendition
  rowId: 216,             // real DB id — used for mutations
  rendition: 'forward',   // 'forward' | 'reversed'
  r2_key: '...',
  r2_reversed_key: '...', // both keys always attached
  name, artist_id, position, label,
  parsedTrackId, durationSec,
}
```

Groups by `(artist_id, name)`. Total counting: `tracks` = unique `rowId`s, `clips` = renditions.

`useCloudflareTrackMutations()` exposes:
- `edit(id, body)` → PUT
- `remove(id)` → DELETE slot
- `removeReversed(id)` → DELETE `/reversed`
- `reverse({ id, replace })` → POST `/reverse`
- `isEditing/isRemoving/isRemovingReversed/isReversing` + corresponding `*Id` and `*Error`
