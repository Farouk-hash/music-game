## 🚀 V2 POOL ARCHITECTURE (Zero-D1 Round Fetch)

### Design principles (MANDATORY)
1. **Never load the whole pool in one request.** A request loads only a small "work set" of 5–8 artists via `workSetFor(scopeArtistIds, count)`.
2. **No D1 queries inside per-round/per-question code.** Use the catalog (KV, memoized) or already-loaded artist data. D1 is only for cold-cache fallback or one cached last-resort query.
3. **In-isolate memo caches RESOLVED values only** (TTL 60s). Never share pending promises.
4. **Never mutate arrays/objects from pool/catalog data.** Copy first (`arr.slice()`) before shuffling.
5. **Hard cap per request:** `MAX_ROUNDS_PER_REQUEST = 50`. Over-fetch candidates 3x.
6. **Respect free-tier KV write limits:** 2 keys per artist on rebuild. Rebuild is pageable.

### New KV layout (`src/lib/cache/pool.js`)
- `pool:v2:core:{artistId}` = `{ t: tracks[], i: instruments[], y: {album_name: year}, s: snippets[] }`
- `pool:v2:lyr:{artistId}` = array of full lyric rows.

### Exports from `src/lib/cache.js`
- `PoolNotReady`, `loadArtistData(env, kind, artistIds)`, `peekLoaded(kind)`
- `buildPoolForArtists(env, ids)`, `buildAndStorePools(env, { offset, limit })`
- `invalidatePools(env)`, `getCatalogFromKV(env)`, `buildCatalogIndex(catalog)`

## 🔄 DEPLOYMENT WORKFLOW (TWO MODES)

### Mode 1: Full rebuild (one-time, after schema changes or first deploy)
Run the pagination script once:
```javascript
// rebuild-pools.js
const ADMIN_KEY = 'aB3xK9mN2pQ7rT4v';
const BASE_URL = 'https://music-game-wrangler.abdulrahman-muhammad2090.workers.dev';
async function rebuildPools() {
  let offset = 0, done = false, totalArtists = 0;
  while (!done) {
    const res = await fetch(`${BASE_URL}/game/catalog/invalidate?admin_key=${ADMIN_KEY}&offset=${offset}&limit=25`, { method: 'POST' });
    const data = await res.json();
    if (totalArtists === 0 && data.totalArtists) totalArtists = data.totalArtists;
    if (data.done) done = true; else { offset = data.nextOffset; await new Promise(r => setTimeout(r, 300)); }
  }
}
rebuildPools();
```
Run: `node rebuild-pools.js`

### Mode 2: Incremental rebuild (daily admin uploads)

## 🎮 UNIFIED PLAY UI ARCHITECTURE (v82)

To eliminate duplication while respecting Level 3's unique 2-phase layout, the UI is structured as follows:

### 1. `PlayView.jsx` (Dedicated to Level 1 & 2)
Handles the outer shell: `Loader`, `ErrorBlock`, `EmptyBlock`, `EndScreen`, `RoundHeader`, and `ProgressBar`. 
It contains the default layouts for Level 1 (vertical stack) and Level 2 (horizontal top bar).

### 2. `useGameEngine.js` (Level 1 & 2)
Centralizes state: `usePlaySession`, `useLifelines`, `useRoundReversal`, and default lifeline handlers (`handleSkip`, `handleRemove`, `handleReveal`, `handleReplay`).

### 3. `useGameEngineL3.js` (Level 3 Specific)
Bridges the gap between `useRoundSet` (which returns `data.sets`) and `usePlaySession` (which expects `rounds`).
```javascript
export function useGameEngineL3(fetchHook, params) {
  const { data, isLoading, error, refetch } = fetchHook(params);
  const sets = data?.sets ?? [];
  const session = usePlaySession(sets, { timerSeconds: params.timerSeconds });
  const lifelines = useLifelines({ skips: params.skips ?? 0, removes: params.removes ?? 0, reveals: params.reveals ?? 0 }, params.count);
  const totalLifelineCost = Object.values(session.roundScores).reduce((sum, r) => sum + (r.cost || 0), 0);
  const handleReplay = async () => { await refetch(); lifelines.reset(); session.restart(); };
  return { rounds: sets, isLoading, error, session, lifelines, totalLifelineCost, handleReplay };
}
```

### 4. `Play3.jsx` (Standalone but Unified Shell)
Uses `useGameEngineL3` for state. Renders the unified `RoundHeader` and `ProgressBar` at the top, followed by its unique 2-phase UI (`MultiClipPlayer` → `QuestionCard` → `RevealedTracks`). 
Lifelines are fully wired using `session.pick`, `session.skip`, `session.revealAnswer`, `session.hideOption`, and `session.next`.
