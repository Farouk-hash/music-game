## D1 Schema

```sql
CREATE TABLE genres (
  id INTEGER PRIMARY KEY,
  name TEXT NOT NULL UNIQUE,
  display_name TEXT NOT NULL,
  image TEXT,
  is_customized INTEGER NOT NULL DEFAULT 0
);

CREATE TABLE artists (
  id INTEGER PRIMARY KEY,
  name TEXT NOT NULL,
  genre_ids TEXT NOT NULL DEFAULT '[]',
  image TEXT,
  tracks_count INTEGER NOT NULL DEFAULT 0,
  is_customized INTEGER NOT NULL DEFAULT 0,
  created_at TEXT NOT NULL DEFAULT (datetime('now')),
  updated_at TEXT NOT NULL DEFAULT (datetime('now'))
);

CREATE TABLE tracks (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  name TEXT NOT NULL,
  artist_id INTEGER,
  r2_key TEXT,
  r2_reversed_key TEXT,
  position TEXT,             -- start | middle | end | custom
  label TEXT,
  album_name TEXT,
  featured_artists TEXT
);
CREATE UNIQUE INDEX idx_tracks_unique_clip ON tracks(artist_id, name, position);

-- NEW this session
CREATE TABLE lyrics (
  id            INTEGER PRIMARY KEY AUTOINCREMENT,
  artist_id     INTEGER NOT NULL,
  track_name    TEXT    NOT NULL,
  lyrics        TEXT,
  created_at    TEXT    NOT NULL DEFAULT (datetime('now')),
  updated_at    TEXT    NOT NULL DEFAULT (datetime('now'))
);
CREATE UNIQUE INDEX idx_lyrics_unique ON lyrics(artist_id, track_name);
CREATE INDEX idx_lyrics_artist ON lyrics(artist_id);
```

**Key semantics:**
- One `tracks` row = one slot = `(artist_id, name, position)`. Both forward and reversed renditions live on the same row.
- One `lyrics` row = one song = `(artist_id, track_name)`. Multiple `tracks` rows with the same `(artist_id, name)` share one `lyrics` row.
- `artists.tracks_count` — should be `COUNT(DISTINCT t.name)` per artist. Backfill SQL was provided.

### 2. Lyrics source facts (confirmed this session)

**matb3aa** — first-choice source, same site the audio pipeline uses:

```
GET https://www.matb3aa.com/api/v1/search?query={name}&loader=searchPage
Headers: User-Agent (browser), Referer: https://www.matb3aa.com/, Origin: https://www.matb3aa.com
→ { results: { tracks: { data: [{ id, name, artists: [{id}], album: {...}, duration }] } } }

GET https://www.matb3aa.com/api/v1/tracks/{id}/lyrics?duration=0
→ { is_synced: false, lines: [{ text }], status: "success" }
```

Match rule: `result.name === track.name` AND `result.artists[].id` includes `track.artist_id`.
- 98.2% match rate observed on artist 65 (270 / 275)
- Fetches succeed for ~71% of matched IDs; the rest return `{"message": "تعذر إحضار..."}` = "no lyrics available" (not an error)
- **`fetch-failed` label is wrong** for those 29% — it should be `no-lyrics-available`. Low priority to fix.

**lyrics.nu** — fallback source:

```
/singer/{singer-slug}/page/{N}/  → song list (60 per page)
/kalimat-aghani/{song-slug}/{singer-slug}/  → HTML with <section class="w3-container w3-margin-bottom">LYRICS</section>
```

- Slug resolution via `/singers-names-that-start-with/{letter}/`
- Arabic normalization + Levenshtein matching
- ~79% match rate on artist 65 (216 / 275)
- `fetch-failed` and `no-lyrics-section` are real miss reasons

### 3. Compare rules (in `run.js`)

- **Discard** matb3aa entries with `charCount < 100` (they're placeholders like `"كلمات اغنية X - Y"`)
- **Keep** all lyrics.nu entries
- **Only one source has lyrics** → that one wins
- **Both have lyrics** → **longest wins**; tie goes to matb3aa
- **Neither** → track skipped

### 4. Pipeline jobs API (Express)

```
POST /api/pipeline/jobs
  body: { scope: 'artist', artistId: 65 }
       | { scope: 'artists', artistIds: [65,9,42] }
       | { scope: 'missing-only' }
  → { job: { id, status: 'starting', ... } }

GET /api/pipeline/jobs/:id
  → { job: { id, status, stage, progress: {done,total}, summary, log, error } }

POST /api/pipeline/jobs/:id/cancel
  → { ok: true, job }

GET /api/pipeline/jobs
  → { jobs: [...] }
```

- In-memory registry (`server/lib/job-registry.js`). Not persisted — jobs vanish on server restart.
- Child spawned via `server/routes/pipeline-routes.js`. Parses JSON lines from stdout, updates job record.
- `SIGKILL` on cancel. Partial D1 writes persist; re-run is idempotent (upsert on `(artist_id, track_name)`).

### 5. Worker `/lyrics` routes

```
GET    /lyrics                    list w/ filters (artist_id, search, has_lyrics, limit, offset)
GET    /lyrics/stats              total/withLyrics/withoutLyrics + perArtist[]
GET    /lyrics/by-track           ?artist_id=&track_name=
GET    /lyrics/:id
POST   /lyrics                    { artist_id, track_name, lyrics }
POST   /lyrics/bulk               { items: [...] } — max 200 per request
PUT    /lyrics/:id                { lyrics }
DELETE /lyrics/:id
```

**All read queries LEFT JOIN artists** so responses include `artist_name`. Search matches track_name OR artist name.

**Critical routing gotcha:** the Worker's route matcher uses **named capture groups** (`(?<id>\d+)`), NOT positional `(\d+)`. Positional groups silently fail — the handler receives `{}` and `id` is `undefined`. Every parameterized route must use `(?<id>\d+)` and read `p.id` from the third arg.
