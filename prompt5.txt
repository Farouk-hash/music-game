## Reversed Audio Rendition — IN PROGRESS

**Purpose:** let the player choose to hear the *reversed* rendition of each clip instead of the forward one.

**Param name:** `rendition` — `'forward'` (default, omitted from URL) or `'reverse'`.

**Distinct from `reversed`:** the existing `reversed=no|some|all` URL param is the *answer-scramble* toggle (scrambles text), NOT the audio. Two separate params, clearly named.

**Fallback rule (agreed):** scope-level. If any reversed slots exist in scope, use them all; if none exist, use forward for everything. Worker reports `meta.requestedRendition` and `meta.usedRendition`.

**Correctly verified in the Worker:** a curl to `/game/round-multiplayer?genres=45&rendition=reverse&level=1&players=2&count=5` returned `meta.usedRendition: "reverse"` and clips with `-rev.mp3` in the `r2_key` for some rounds.

**PENDING BUG:** In the same response, some audio rounds had **forward** `r2_key` values (no `-rev.mp3`) despite `usedRendition: "reverse"`. That's the mixed-rendition symptom. Diagnosis in progress:

The full chain that must be wired:
1. `slotsForArtist(env, artistId, years, rendition)` — 4th param must select `r2_reversed_key IS NOT NULL` when `rendition === 'reverse'`, and remap the returned row's `r2_key` to point at the reversed object.
2. `pickSlotsVaried(env, artistIds, count, years, rendition)` — 5th param must forward `rendition`.
3. Each round controller (`rounds.js`, `round-mutli.js`) must call `pickSlotsVaried(..., rendition)`.
4. `meta` must include `requestedRendition` and `usedRendition`.

**If any of these four is missing, forward slots leak into a `rendition=reverse` request.** The `usedRendition` field is set by a separate code path from the actual slot query, so it can read `"reverse"` even when forward slots are used.

**Critical:** `music-game-wrangler/src/controllers/game/rounds-methods/slots.js` needs to be inspected. It may still have the old `slotsForArtist(env, artistId, years)` signature without `rendition` handling.

## Reverse-Batch Feature — Working

**Purpose:** bulk-generate reversed renditions for every slot that has a forward clip but no reversed clip.

**Server:**
- `server/scripts/reverse-batch.js` — child process. Reads `--ids-file=<path>` (JSON array of slot IDs). For each ID: fetches the track, parses `r2_key`, calls `reverseExistingClip`, PUTs the new key. Emits JSON progress lines.
- `POST /api/cloudflare/tracks/reverse-batch` — endpoint in `server/routes/cloud-flare-routes/clips.js`. Queries the Worker for slots with `has_forward=1&has_reversed=0&limit=20000`, writes IDs to a temp file, spawns the child. Returns `{ job, count }`.
- **Route ordering:** `router.post('/tracks/reverse-batch', ...)` must be **before** `router.post('/tracks/:id/reverse', ...)`.
- Reuses `server/lib/job-registry.js`.
- Cancellable via `POST /api/pipeline/jobs/:id/cancel`.

**Client:**
- `admin/src/hooks/useReverseBatchJob.js` — polls `/pipeline/jobs/:id`.
- `admin/src/routes/PublishedTracks.jsx` — "Reverse missing" button (with count badge), confirmation modal, `PipelineJobPanel` for progress. Refetches tracks on job completion.
- `admin/src/components/domain/PipelineJobPanel.jsx` — added `reverse: 'Reversing clips'` stage label + summary fields (`total`, `reversed`, `skipped`).
- **CRITICAL FIX:** `useCloudflareTrackMutations.js` returns `startReverseBatch.mutateAsync` (was `.mutate`, which returned `undefined` and blocked the modal).

**Known limitation:** before the `has_reversed=0` fix, the batch route requested `/tracks?has_forward=1&limit=1000` and filtered locally. With 17k+ tracks needing reverse, each batch saw only 1000 rows. The fix is to add `has_reversed=0` to the query so the Worker returns only the missing slots. **Verify this fix is applied.** If the batch processes far fewer clips than the client shows, the `has_reversed=0` change is missing.
